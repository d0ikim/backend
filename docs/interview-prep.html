🔑 Token Rotation 핵심: 갱신할 때마다 Refresh Token을 교체 → 탈취된 토큰으로 재시도하면 DB 값과 다르므로 거부됨

핵심 코드 — TokenProvider

// Access Token 발급 (30분)
return Jwts.builder()
    .signWith(SignatureAlgorithm.HS512, jwtProperties.getSecretKey())
    .setSubject(userEntity.getUserId())  // sub: userId
    .setIssuer("cafeOn")
    .setIssuedAt(new Date())
    .setExpiration(Date.from(Instant.now().plus(30, ChronoUnit.MINUTES)))
    .claim("tokenType", "access")
    .claim("role", userEntity.getRole().name())
    .compact();

핵심 코드 — 로그아웃 (RefreshToken 무효화)

public void logout(String authorizationHeader) {
    String token = authorizationHeader.substring(7); // "Bearer " 제거
    Map claims = tokenProvider.validateAndExtractClaims(token, "access");
    String userId = claims.get("userId");

    userRepository.findById(userId).ifPresent(user -> {
        user.setRefreshToken(null);  // DB에서 Refresh 제거
        userRepository.save(user);
    });
}

💬 면접 예상 Q&A

▶ 클릭해서 답변 확인

JWT JWT를 사용한 이유가 뭔가요? ▶

세션 방식은 서버에 상태를 저장해서 서버가 여러 대일 때 세션 동기화 문제가 생깁니다. JWT는 토큰 자체에 사용자 정보를 담아 서버가 무상태(Stateless)로 동작할 수 있어 수평 확장에 유리합니다. AWS EC2에 배포하고 이후 스케일아웃을 고려해 JWT를 선택했습니다.

JWT Refresh Token을 DB에 저장하는 이유가 뭔가요? ▶

DB에 저장하지 않으면 토큰이 탈취됐을 때 서버에서 무효화할 방법이 없습니다. 로그아웃 시 DB의 refresh_token을 null로 만들면 이후 갱신 요청을 모두 거부할 수 있습니다. 또한 Token Rotation 전략으로 갱신할 때마다 새 Refresh Token으로 교체해 탈취된 토큰 재사용을 방지했습니다.

JWT Token Rotation이 무엇이고 왜 적용했나요? ▶

Refresh Token을 한 번 사용하면 새로운 Refresh Token으로 교체하는 전략입니다. 탈취된 토큰 감지가 가능합니다. 정상 사용자가 먼저 갱신하면 DB 값이 바뀌고, 공격자가 이전 토큰으로 재시도하면 DB 값과 달라 거부됩니다. 코드에서는 갱신 시 DB의 Refresh Token 값과 요청값을 비교하고, 일치할 때만 새 쌍을 발급합니다.

카카오 카카오 API 결과를 DB와 병합한 이유는요? ▶

카카오 API만 쓰면 서비스 고유 데이터(리뷰 요약·태그·평점)가 없고, DB만 쓰면 카카오에 있는 신규 카페가 누락됩니다. 두 데이터를 이름 기준으로 병합해서 DB에 있으면 내부 데이터를, 없으면 카카오 데이터를 보여줍니다. 신규 카페는 @Async로 백그라운드에서 DB에 저장해 다음 검색부터 내부 데이터를 활용합니다.

카카오 @Async로 비동기 저장한 이유가 뭔가요? ▶

검색 요청마다 신규 카페를 동기로 DB에 저장하면 응답 지연이 생깁니다. 사용자 입장에서는 저장 완료를 기다릴 필요가 없으니 @Async로 별도 스레드에서 처리해 응답 속도를 개선했습니다. 주의할 점은 @Async는 프록시를 통해야 동작하므로 반드시 public 메서드로 분리해야 합니다. 또한 @Transactional과 함께 써서 저장 실패 시 롤백됩니다.

성능 N+1 문제를 어떻게 해결했나요? ▶

카페 목록 100개에서 각각 태그를 조회하면 101번 쿼리가 발생합니다. findTagNamesByCafeIds(cafeIds)로 IN 절 배치 조회를 사용하고 결과를 Map<Long, List<String>>으로 변환해 카페별로 매핑했습니다. 리뷰도 getReviewsByCafeIds(cafeIds)로 동일하게 처리했습니다. 검색 목록에서는 리뷰를 빈 배열로 반환해 불필요한 조회를 차단했습니다.

설계 Soft Delete를 적용한 이유가 뭔가요? ▶

사용자 데이터를 물리적으로 삭제하면 해당 유저가 작성한 리뷰·게시글과의 관계가 끊어져 데이터 정합성이 깨집니다. Hibernate의 @SQLDelete와 @Where를 사용해 deleted_at 컬럼으로 논리 삭제를 구현했습니다. 탈퇴한 사용자는 닉네임을 '탈퇴회원'으로 변경해 게시글/댓글에서 표시할 수 있게 했습니다. 쿼리에서는 @Where로 자동 필터링되어 탈퇴 유저가 조회되지 않습니다.

설계 BCrypt를 선택한 이유는요? ▶

BCrypt는 단방향 해시 + salt 자동 적용으로 같은 비밀번호도 매번 다른 해시값이 나와 Rainbow Table 공격을 방어합니다. work factor를 조절해 연산 비용을 높일 수 있습니다. Spring Security가 기본으로 제공하는 PasswordEncoder여서 matches() 메서드로 쉽게 검증할 수 있습니다.

DB ST_Distance_Sphere를 사용한 이유는요? ▶

위도/경도 좌표 간 거리를 평면 거리 공식으로 계산하면 지구의 곡률이 고려되지 않아 오차가 생깁니다. MySQL의 ST_Distance_Sphere()는 하버사인 공식 기반으로 지구 구면 거리를 정확하게 계산합니다. 반경 검색 특성상 인덱스 활용이 어렵지만 LIMIT 100으로 결과를 제한해 성능을 보완했습니다. DB 결과가 10개 미만이면 카카오 Category API로 보완합니다.

DB em.getReference()를 쓴 이유가 뭔가요? ▶

위시리스트 토글 시 CafeEntity의 실제 데이터는 필요 없고 FK 참조만 있으면 됩니다. em.getReference()는 프록시 객체만 생성하고 실제 DB 조회를 하지 않아 불필요한 SELECT 쿼리를 줄일 수 있습니다. 단 존재하지 않는 cafeId를 넘기면 나중에 DataIntegrityViolationException이 발생하므로 이를 catch해서 처리했습니다.

개선 개선하고 싶은 점이 있나요? ▶

세 가지를 개선하고 싶습니다. 첫째, 임시 비밀번호 방식 → 일회용 링크 방식으로 변경 (UUID 토큰 + 만료시간 저장). 둘째, 카페 상세 조회 시마다 UPDATE 쿼리가 발생하는 조회수 증가를 Redis로 비동기 집계하면 성능이 개선됩니다. 셋째, 소셜 로그인(Google, Kakao)을 OAuth2로 구현하지 못했는데 Spring Security OAuth2를 활용해 추가할 수 있습니다.
