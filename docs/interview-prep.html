핵심 코드 — Access Token 발급

return Jwts.builder()
    .signWith(SignatureAlgorithm.HS512, jwtProperties.getSecretKey())
    .setSubject(userEntity.getUserId())  // sub: userId
    .setIssuer("cafeOn")
    .setIssuedAt(new Date())
    .setExpiration(Date.from(Instant.now().plus(30, ChronoUnit.MINUTES)))
    .claim("tokenType", "access")
    .claim("role", userEntity.getRole().name())
    .compact();

💬 면접 예상 Q&A

▶ 탭해서 답변 확인

JWT JWT를 사용한 이유가 뭔가요?
▶

세션 방식은 서버에 상태를 저장해서 서버가 여러 대일 때 세션 동기화 문제가 생깁니다. JWT는 토큰 자체에 사용자 정보를 담아 서버가 무상태(Stateless)로 동작할 수 있어 수평 확장에 유리합니다. AWS EC2에 배포하고 스케일아웃을 고려해 JWT를 선택했습니다.

JWT Refresh Token을 DB에 저장하는 이유가 뭔가요?
▶

DB에 저장하지 않으면 토큰이 탈취됐을 때 서버에서 무효화할 방법이 없습니다. 로그아웃 시 DB의 refresh_token을 null로 만들면 이후 갱신 요청을 모두 거부할 수 있습니다. 또한 Token Rotation 전략으로 갱신 때마다 새 토큰으로 교체해 탈취된 토큰 재사용을 방지했습니다.

JWT Token Rotation이 무엇이고 왜 적용했나요?
▶

Refresh Token을 한 번 사용하면 새 토큰으로 교체하는 전략입니다. 탈취된 토큰 감지가 가능합니다. 정상 사용자가 먼저 갱신하면 DB 값이 바뀌고, 공격자가 이전 토큰으로 재시도하면 DB 값과 달라 거부됩니다. 코드에서는 갱신 시 DB 값과 요청값을 비교하고 일치할 때만 새 쌍을 발급합니다.

카카오 카카오 API 결과를 DB와 병합한 이유는요?
▶

카카오 API만 쓰면 서비스 고유 데이터(리뷰 요약·태그·평점)가 없고, DB만 쓰면 신규 카페가 누락됩니다. 이름 기준으로 병합해서 DB에 있으면 내부 데이터를, 없으면 카카오 데이터를 보여줍니다. 신규 카페는 @Async로 백그라운드에서 DB에 저장해 다음 검색부터 내부 데이터를 활용합니다.

카카오 @Async로 비동기 저장한 이유가 뭔가요?
▶

검색 요청마다 신규 카페를 동기로 DB에 저장하면 응답 지연이 생깁니다. 사용자는 저장 완료를 기다릴 필요가 없으니 @Async로 별도 스레드에서 처리해 응답 속도를 개선했습니다. 주의할 점은 @Async는 프록시를 통해야 동작하므로 반드시 public 메서드로 분리해야 합니다.

성능 N+1 문제를 어떻게 해결했나요?
▶

카페 목록 100개에서 각각 태그를 조회하면 101번 쿼리가 발생합니다. findTagNamesByCafeIds(cafeIds)로 IN 절 배치 조회를 사용하고 결과를 Map<Long, List<String>>으로 변환해 카페별로 매핑했습니다. 검색 목록에서는 리뷰를 빈 배열로 반환해 불필요한 조회를 차단했습니다.

설계 Soft Delete를 적용한 이유가 뭔가요?
▶

사용자 데이터를 물리 삭제하면 해당 유저의 리뷰·게시글과의 관계가 끊어져 데이터 정합성이 깨집니다. Hibernate @SQLDelete + @Where로 논리 삭제를 구현했습니다. 탈퇴 유저는 닉네임을 '탈퇴회원'으로 변경해 게시글에 표시하고, @Where 필터로 일반 쿼리에서는 자동으로 제외됩니다.

설계 BCrypt를 선택한 이유는요?
▶

BCrypt는 단방향 해시 + salt 자동 적용으로 같은 비밀번호도 매번 다른 해시값이 나와 Rainbow Table 공격을 방어합니다. work factor를 조절해 연산 비용을 높일 수 있습니다. Spring Security 기본 PasswordEncoder여서 matches()로 간편하게 검증할 수 있습니다.

DB ST_Distance_Sphere를 사용한 이유는요?
▶

평면 거리 공식은 지구 곡률이 고려되지 않아 오차가 생깁니다. MySQL ST_Distance_Sphere()는 하버사인 공식 기반으로 구면 거리를 정확하게 계산합니다. 반경 검색 특성상 인덱스 활용이 어렵지만 LIMIT 100으로 제한해 성능을 보완했고, DB 결과 부족 시 카카오 Category API로 보완합니다.

DB em.getReference()를 쓴 이유가 뭔가요?
▶

위시리스트 토글 시 CafeEntity 실제 데이터는 필요 없고 FK 참조만 있으면 됩니다. getReference()는 프록시 객체만 생성하고 실제 DB 조회를 안 해서 불필요한 SELECT를 줄일 수 있습니다. 존재하지 않는 cafeId면 나중에 DataIntegrityViolationException이 발생하므로 catch로 처리했습니다.

개선 개선하고 싶은 점이 있나요?
▶

세 가지를 꼽겠습니다. 첫째, 임시 비밀번호 방식을 UUID 토큰 + 만료시간 DB 저장 방식의 일회용 링크로 교체해 보안을 강화하고 싶습니다. 둘째, 상세 조회마다 발생하는 조회수 UPDATE를 Redis로 버퍼링 후 배치 반영해 DB 부하를 줄이고 싶습니다. 셋째, 시간 부족으로 구현 못한 OAuth2 소셜 로그인(Google·Kakao)을 Spring Security OAuth2 Client로 추가하고 싶습니다.

JWT Access Token과 Refresh Token의 역할 차이는 뭔가요?
▶

TokenProvider.issueAccessToken()은 만료 30분짜리로 매 API 요청 헤더에 담아 보냅니다. issueRefreshToken()은 만료 14일짜리로 Access Token이 만료됐을 때 재발급받는 용도입니다. Access Token을 짧게 유지해 탈취 위험을 줄이고, Refresh Token을 길게 유지해 사용자 재로그인 빈도를 낮춥니다.

JWT 로그아웃을 어떻게 구현했나요?
▶

AuthController.logout()에서 Authorization 헤더의 Access Token을 받아 TokenProvider.validateAndExtractClaims(token, "access")로 검증 후 userId를 추출합니다. userRepository.findById(userId)로 유저를 조회해 user.setRefreshToken(null)을 호출하고 save합니다. 이후 클라이언트가 /api/auth/refresh를 요청하면 DB에 null이 저장되어 있어 거부됩니다.

JWT JwtAuthenticationFilter는 어떻게 동작하나요?
▶

OncePerRequestFilter를 상속해 모든 요청에 한 번씩 실행됩니다. Authorization 헤더에서 "Bearer " 뒤 토큰을 추출해 TokenProvider.validateAndExtractClaims(token, "access")를 호출합니다. 유효하면 UsernamePasswordAuthenticationToken(userId, null, authorities)를 생성해 SecurityContextHolder에 저장합니다. /api/auth/refresh 경로는 Access Token 검증에서 제외했습니다.

JWT Access Token이 만료됐을 때 클라이언트는 어떻게 처리하나요?
▶

서버는 TokenProvider.validateAndExtractClaims()에서 ExpiredJwtException이 발생하면 null을 반환하고, 인증 필요 API는 401을 응답합니다. 클라이언트는 401을 받으면 저장해둔 Refresh Token을 담아 POST /api/auth/refresh를 호출합니다. 성공하면 새 Access + Refresh Token을 저장하고 원래 요청을 재시도하도록 프론트엔드와 합의해 설계했습니다.

Security JWT의 단점은 무엇이고 어떻게 보완했나요?
▶

JWT는 발급 후 만료 전까지 서버에서 강제 무효화가 어렵습니다. 두 가지로 보완했습니다. 첫째, Refresh Token을 DB에 저장해 로그아웃 시 null로 무효화했습니다. 둘째, Access Token 유효기간을 30분으로 짧게 유지해 탈취되더라도 피해 시간을 최소화했습니다. 완벽하지 않지만 실용적인 트레이드오프입니다.

Security Spring Security FilterChain이란?
▶

HTTP 요청이 Controller에 도달하기 전 순서대로 거치는 필터들의 체인입니다. SecurityConfig.filterChain()에서 경로별 접근 권한을 설정하고, http.addFilterAfter(jwtAuthenticationFilter, CorsFilter.class)로 CORS 처리 이후 JWT 검증이 실행되도록 순서를 지정했습니다. SessionCreationPolicy.STATELESS로 세션을 생성하지 않습니다.

Security CSRF를 비활성화한 이유는?
▶

CSRF 공격은 브라우저가 세션 쿠키를 자동으로 첨부할 때 발생합니다. 이 프로젝트는 JWT를 Authorization 헤더에 직접 담아 전송하므로 브라우저가 자동 첨부하지 않아 CSRF 위협이 없습니다. SecurityConfig에서 .csrf(CsrfConfigurer::disable)로 비활성화해 불필요한 처리를 제거했습니다.

Security ROLE_ADMIN > ROLE_USER 계층은 어떻게 구현했나요?
▶

SecurityConfig에서 RoleHierarchyImpl.fromHierarchy("ROLE_ADMIN > ROLE_USER") 빈을 등록했습니다. 이렇게 하면 ROLE_USER 권한이 필요한 모든 API에 ROLE_ADMIN도 자동으로 접근할 수 있습니다. 리뷰 수정/삭제에서 관리자가 모든 리뷰를 관리할 수 있도록 이 설정을 활용했습니다.

Security HS512 알고리즘을 선택한 이유는?
▶

HS512는 HMAC-SHA512 방식으로 서버 하나의 비밀키로 서명과 검증을 모두 수행합니다. RS256 같은 비대칭 알고리즘은 공개키/개인키 쌍이 필요해 단일 서버 구조에서는 불필요한 복잡성이 생깁니다. 단일 서버 구조에서는 HS512가 구현이 간단하면서도 충분히 안전합니다.

Security SecurityContextHolder는 무엇인가요?
▶

현재 요청 스레드의 인증 정보를 보관하는 컨텍스트입니다. JwtAuthenticationFilter에서 토큰 검증 후 SecurityContextHolder.getContext().setAuthentication(authentication)으로 저장합니다. 이후 같은 요청 내 어느 레이어에서든 getAuthentication()으로 꺼낼 수 있어, 리뷰 수정/삭제 시 ROLE_ADMIN 확인에 활용했습니다.

Security CORS를 어떻게 설정했나요?
▶

SecurityConfig.corsConfigurationSource()에서 허용 Origin을 "*"(와일드카드), 허용 메서드를 GET/POST/PUT/DELETE/PATCH/OPTIONS로 설정했습니다. setAllowCredentials(true)로 쿠키·인증 헤더를 허용했습니다. 현재는 개발 편의상 와일드카드를 썼지만 실서비스에서는 프론트엔드 도메인으로 제한해야 한다는 점을 인지하고 있습니다.

JPA / Hibernate
JPA @Transactional의 역할은?
▶

메서드 실행을 하나의 트랜잭션으로 묶어 중간에 예외가 발생하면 전체를 롤백합니다. AuthService.refreshTokens()에서 새 Refresh Token을 DB에 저장하다 오류가 나면 이전 상태로 되돌아갑니다. @Async @Transactional을 함께 쓴 synchronizeCafe()는 별도 스레드에서 독립적인 트랜잭션으로 실행됩니다.

JPA @Transactional(readOnly=true)를 쓴 이유는?
▶

CafeService 클래스 레벨에 @Transactional(readOnly = true)를 선언했습니다. 읽기 전용 트랜잭션은 영속성 컨텍스트의 변경감지(Dirty Checking)를 생략해 성능이 약간 향상되고 실수로 데이터를 수정하는 것도 방지합니다. 조회수 증가처럼 쓰기가 필요한 메서드에는 @Transactional을 별도로 붙여 오버라이드했습니다.

JPA Lazy Loading을 사용한 이유는?
▶

ReviewEntity의 user, cafe 필드에 FetchType.LAZY를 설정했습니다. Eager Loading이면 리뷰 조회 시 항상 User와 Cafe 전체를 JOIN해서 가져오는데, 대부분의 조회에서 연관 객체 전체 데이터가 필요하지 않습니다. Lazy Loading으로 실제 접근 시점에만 추가 쿼리를 발생시켜 불필요한 데이터 로딩을 막았습니다.

JPA @PrePersist는 무엇인가요?
▶

JPA가 Entity를 처음 저장하기 직전에 실행되는 콜백 메서드에 붙이는 어노테이션입니다. ReviewEntity에서 @PrePersist로 createdAt = LocalDateTime.now()를 자동 설정했습니다. UserEntity는 @PrePersist와 @PreUpdate 모두 사용해 createdAt/updatedAt을 일관되게 관리했습니다.

JPA cascade=ALL과 orphanRemoval=true의 차이는?
▶

ReviewEntity.images에 두 옵션을 모두 설정했습니다. cascade=ALL은 Review 저장/삭제 시 연관 ImageEntity도 함께 저장/삭제합니다. orphanRemoval=true는 images 리스트에서 특정 ImageEntity를 제거하면 자동으로 DELETE 쿼리가 실행됩니다. 단 DB 삭제와 별개로 S3 실제 파일은 S3Service.delete(s3Key)를 별도 호출해야 합니다.

JPA @Async와 @Transactional을 함께 쓸 때 주의점은?
▶

@Async 메서드는 별도 스레드에서 실행되므로 호출자의 트랜잭션에 참여하지 않습니다. synchronizeCafe()에 @Transactional을 별도로 선언한 이유입니다. 또한 @Async는 Spring AOP 프록시를 통해야 작동하므로 반드시 public 메서드여야 하고, 같은 클래스 내부에서 직접 호출하면 프록시를 우회해 동기로 실행됩니다.

JPA Builder 패턴을 Entity에서 사용한 이유는?
▶

Lombok의 @Builder를 붙여 UserEntity.builder().name().email().password().build() 방식으로 생성했습니다. 생성자 파라미터 순서를 외울 필요 없이 필드 이름으로 값을 지정하므로 가독성이 높고 실수가 줄어듭니다. AuthService.signUp()에서 회원가입 시 빌더로 Entity를 생성하는 코드가 그 예시입니다.

DB 설계
DB userId를 UUID로 설계한 이유는?
▶

Auto-increment 정수 PK는 1, 2, 3처럼 순차적이라 외부 노출 시 전체 사용자 수 파악이나 순차 탐색 공격에 취약합니다. UUID.randomUUID()는 예측 불가능하고 분산 환경에서도 충돌 없이 생성할 수 있어 보안과 확장성이 유리합니다. AuthService.signUp()에서 UUID를 생성해 userId로 사용했습니다.

DB EnumType.STRING을 사용한 이유는?
▶

EnumType.ORDINAL은 Enum 순서의 정수(0, 1, 2…)를 저장해 Enum 중간에 값을 추가하면 기존 데이터 매핑이 틀어집니다. EnumType.STRING은 "ACTIVE", "USER" 같은 문자열을 저장해 Enum 순서 변경에 영향받지 않고 DB에서 바로 의미를 파악할 수 있습니다. 유지보수와 가독성을 위해 STRING을 선택했습니다.

DB DDL Auto를 validate로 설정한 이유는?
▶

create나 update는 실수로 테이블을 재생성하거나 컬럼을 변경해 운영 데이터를 날릴 위험이 있습니다. validate는 기존 스키마가 Entity와 일치하는지만 확인하고 변경하지 않아 프로덕션 환경에서 안전합니다. 스키마 변경은 별도 마이그레이션 스크립트로 관리하는 것이 원칙입니다.

DB 인덱스는 어떻게 설계했나요?
▶

WishlistEntity에 @Index(columnList = "user_id")와 @Index(columnList = "cafe_id")를 설정해 사용자별 찜 목록 조회와 카페별 찜 수 집계 쿼리 성능을 높였습니다. UserEntity의 email은 로그인마다 조회되므로 UNIQUE 제약이 인덱스 역할을 합니다. CafeEntity의 kakaoId는 existsByKakaoId() 중복 체크에 활용됩니다.

DB 외래키 제약조건 위반을 어떻게 처리했나요?
▶

WishlistService.toggle()에서 em.getReference()로 프록시를 생성하다가 존재하지 않는 cafeId면 저장 시점에 DataIntegrityViolationException이 발생합니다. 이를 try-catch로 잡아 클라이언트에 400 에러를 반환했습니다. GlobalExceptionHandler에서도 공통으로 처리해 예외별 적절한 HTTP 상태코드가 반환되도록 했습니다.

DB Wishlist에 UNIQUE(user_id, cafe_id, category)를 설정한 이유는?
▶

같은 사용자가 같은 카페를 같은 카테고리로 중복 저장하는 것을 DB 레벨에서 방지합니다. 단 같은 카페라도 다른 카테고리(예: WORK, ATMOSPHERE)로는 저장 가능하도록 복합 UNIQUE를 설계했습니다. 애플리케이션 레벨의 중복 체크만으로는 동시 요청 시 Race Condition이 발생할 수 있어 DB 제약조건으로 보완했습니다.

DB avgRating은 어떻게 갱신하나요?
▶

리뷰 작성/수정/삭제 이벤트 시 ReviewRepository.findByCafe_CafeId(cafeId)로 전체 리뷰를 조회해 평균을 계산하고 CafeEntity.avgRating을 직접 업데이트합니다. 개선 방향으로는 DB의 AVG() 집계 쿼리를 사용하거나, 리뷰 수와 합계를 별도 컬럼에 유지하는 증분 업데이트 방식이 더 효율적입니다.

API 설계 / 외부 연동
API RESTful하게 설계했다고 볼 수 있나요?
▶

대체로 REST 원칙을 따랐습니다. 리소스를 명사로 표현하고(/api/cafes, /api/reviews), HTTP 메서드로 행위를 구분했습니다. 다만 /api/auth/logout, /api/auth/password/reset처럼 동작이 복잡한 경우 순수 REST보다 RPC에 가까운 URL을 썼습니다. 팀과 실용성과 원칙 사이에서 합의해 결정했습니다.

API multipart/form-data를 어떻게 처리했나요?
▶

리뷰 작성 API에서 JSON 데이터와 이미지 파일을 함께 전송하기 위해 multipart를 사용했습니다. Controller에서 @RequestPart String reviewJson과 @RequestPart List<MultipartFile> images를 받아, ObjectMapper.readValue(reviewJson, ReviewRequestDTO.class)로 JSON을 파싱합니다. @RequestBody로는 파일을 함께 받을 수 없어 이 방식을 선택했습니다.

API 이미지를 S3에 저장한 이유는?
▶

서버 로컬 파일시스템에 저장하면 서버 여러 대에서 파일 동기화 문제가 생기고 재시작 시 데이터가 유실될 수 있습니다. AWS S3는 가용성이 높고 CDN 연동이 쉬우며, SDK v2로 업로드/삭제를 간편하게 구현할 수 있습니다. S3 Key와 URL을 ImageEntity에 저장해 나중에 S3Service.delete(s3Key)로 파일을 삭제합니다.

API Gmail SMTP로 이메일 발송을 어떻게 구현했나요?
▶

EmailService.sendTempPasswordEmail()에서 JavaMailSender를 주입받아 MimeMessage를 생성하고 HTML 형식 이메일을 발송합니다. Gmail App Password를 .env에 저장하고 spring-dotenv로 로드합니다. AuthService.resetPassword()에서 10자리 랜덤 임시 비밀번호를 BCrypt로 암호화해 DB 저장 후 평문을 이메일로 발송합니다.

API ApiResponse<T> 래퍼를 사용한 이유는?
▶

모든 API 응답을 {"message": "...", "data": {...}} 형태로 통일했습니다. 프론트엔드가 응답 형식을 예측할 수 있고, 에러 시에도 같은 구조로 메시지를 전달할 수 있습니다. ApiResponse.<T>builder().message("로그인 성공").data(dto).build() 방식으로 일관되게 사용했습니다.

API Swagger를 도입한 이유는?
▶

springdoc-openapi-starter-webmvc-ui를 의존성에 추가해 http://localhost:8080/api-docs에서 API 문서를 확인할 수 있습니다. 프론트엔드 팀과 API 명세를 공유할 때 별도 문서 작성 없이 Swagger UI에서 직접 테스트할 수 있어 협업 효율이 높아졌습니다. Controller에 @Operation, @ApiResponse로 요청/응답 예시를 직접 작성했습니다.

성능 최적화
성능 조회수를 어떻게 구현했고 개선점은?
▶

getCafeDetail()에서 카페 조회 시마다 entity.setViewCount(+1)하고 save()를 호출합니다. 매 조회마다 UPDATE 쿼리가 발생하는 단점이 있습니다. 개선 방향은 Redis에 조회수를 버퍼링했다가 배치로 DB에 반영하는 방식입니다. 현재는 CafeScheduler로 매일 새벽 3시에 views_last7d = viewCount - lastViewCount를 계산해 최근 7일 조회수를 Hot Score에 활용합니다.

성능 Hot Score 공식은 어떻게 설계했나요?
▶

네이티브 SQL로 계산합니다. 공식은 views_last7d×w7d + viewCount×wAll + avgRating×50×wRate + reviewCount×5×wRev입니다. 가중치를 쿼리 파라미터로 받아 ?w7d=3&wAll=1&wRate=2&wRev=2처럼 외부에서 조정할 수 있게 했습니다. 리뷰 수는 서브쿼리로 집계하며 상위 10개 결과를 반환합니다.

성능 CafeScheduler로 어떤 배치 작업을 했나요?
▶

@Scheduled(cron = "0 0 3 * * *")로 매일 새벽 3시에 실행됩니다. views_last7d = viewCount - lastViewCount를 계산하고 lastViewCount = viewCount로 기준점을 업데이트합니다. 결과적으로 views_last7d는 항상 최근 7일간의 증분 조회수를 나타내 Hot Score 계산에 활용됩니다. CafeOnApplication에 @EnableScheduling을 선언했습니다.

성능 카카오 API 검색 성능은 어떻게 최적화했나요?
▶

세 가지를 적용했습니다. 첫째, 카카오 API는 최대 45페이지를 조회할 수 있지만 검색 목록에서는 첫 페이지 15개만 가져옵니다(size=15, page=1). 둘째, UriComponentsBuilder.encode(StandardCharsets.UTF_8)로 한글 인코딩을 안전하게 처리했습니다. 셋째, 신규 카페 저장은 @Async로 비동기 처리해 검색 API 응답 속도를 보장했습니다.

프로젝트 전반
종합 JWT란 무엇인지 처음부터 설명해주세요.
▶

JWT(JSON Web Token)는 Header.Payload.Signature 세 부분으로 구성된 자가 포함(Self-contained) 토큰입니다. Payload에 userId, role 등을 담고 서버 비밀키로 서명해, 서버가 DB를 조회하지 않아도 토큰만으로 사용자를 식별할 수 있습니다. TokenProvider에서 Jwts.builder()로 생성하고 parseClaimsJws()로 서명을 검증했습니다.

종합 @AuthenticationPrincipal은 어떻게 동작하나요?
▶

JwtAuthenticationFilter에서 UsernamePasswordAuthenticationToken(userId, null, authorities)를 생성해 SecurityContextHolder에 저장합니다. principal을 userId(String)로 설정했기 때문에 Controller 메서드에서 @AuthenticationPrincipal String userId로 바로 주입받을 수 있습니다. 비밀번호 변경 API에서는 Authentication을 직접 파라미터로 받아 authentication.getName()으로 userId를 꺼냈습니다.

종합 구현하면서 가장 어려웠던 부분은?
▶

카카오 API 결과와 DB 데이터 병합 로직이 가장 복잡했습니다. 두 데이터 소스의 카페 식별 기준이 달라(카카오는 kakaoId, DB는 이름) 정확히 매칭하기 어려웠고, 신규 카페를 @Async로 비동기 저장할 때 트랜잭션 범위와 프록시 동작 방식을 이해하는 데 시간이 걸렸습니다. findByNameIn()으로 이름 기준 매칭, existsByKakaoId()로 중복 방지하는 방식으로 해결했습니다.

종합 팀 협업은 어떻게 했나요?
▶

백엔드 3명이 도메인 단위로 역할을 분담했습니다. 저는 User(인증), Cafe, Review, Wishlist를 담당했고, 팀원들은 Chat(WebSocket), Community(게시판/댓글), Admin 파트를 맡았습니다. Git Flow 전략으로 dev 브랜치를 기준으로 기능별 브랜치를 생성해 PR로 합쳤고, API 명세는 Swagger와 공유 문서로 프론트엔드 팀과 연결했습니다.

지원동기 베스트텍에 지원한 가장 큰 이유는?
▶

AIXR 기반 교육 플랫폼에서 백엔드 역량을 실전에 적용하고 싶어서입니다. CafeOn에서 대규모 데이터 파이프라인 설계와 REST API를 처음부터 담당한 경험이 바이브 코딩 솔루션 초기 백엔드 아키텍처 구축 직무와 직접적으로 연결된다고 판단했습니다. 단순 기능 개발이 아닌 실제 사용자 경험에 영향을 미치는 시스템을 설계한다는 방향성도 일치했습니다.

지원동기 바이브 코딩 솔루션이 무엇인지 알고 지원했나요?
▶

AI가 자연어 요구사항을 코드로 변환해주는 방식의 개발 패러다임으로 이해하고 있습니다. 개발자가 세부 구현보다 아키텍처와 비즈니스 로직 설계에 집중할 수 있게 해주는 도구입니다. 베스트텍이 이 솔루션의 초기 백엔드 기반을 구축하는 단계라고 이해했으며, 프로젝트 초기 단계에서 아키텍처를 직접 설계하는 경험을 할 수 있다는 점에서 특히 매력적이었습니다.

지원동기 20명 규모 스타트업을 선택한 이유가 있나요?

"20명 규모의 팀에서 실제 제품에 직접 기여하며 빠르게 성장할 수 있는 환경"을 원했습니다. 대기업은 큰 시스템의 작은 부분을 담당하는 경우가 많지만, 스타트업에서는 초기 아키텍처 결정부터 배포까지 전 과정을 경험할 수 있습니다. CafeOn에서 백엔드 구조 총괄을 맡으면서 이런 환경이 제 성장에 훨씬 효과적이라는 것을 확인했습니다.

지원동기 인턴십 기간 동안 구체적으로 어떤 기여를 할 수 있다고 생각하나요?

바이브코딩 솔루션의 초기 백엔드 아키텍처 구축에 실질적으로 기여하는 것입니다. CafeOn에서 도메인별 패키지 구조 설계, JPA Entity 설계, JWT 인증 구조 구현을 처음부터 담당한 경험이 직접 적용 가능합니다. Swagger 기반 API 문서화와 공통 예외 처리 구조도 빠르게 세팅할 수 있습니다.

지원동기 재즈피아니스트에서 백엔드 개발자로 전환한 계기는?
▶

음악을 하며 느꼈던 불편함—연주자 커뮤니티의 일정 관리, 악보 공유, 레슨 예약 등—을 기술로 해결하고 싶다는 생각이 출발점이었습니다. DB보안솔루션 과정(829시간)으로 기초를 다지고 SeSAC 웹 부트캠프(762시간)로 본격 전환했습니다. "한 곡을 완성하기 위해 구조를 분석하고 반복적으로 개선하는 습관"이 코드 설계와 디버깅에 그대로 적용됐습니다.

지원동기 음악 전공 배경이 개발에 도움이 된 점은?
▶

두 가지입니다. 첫째, 구조를 분석하고 반복 개선하는 습관이 코드 아키텍처 설계에 그대로 연결됩니다. 둘째, 음악은 이론과 구조 위에서만 자유로울 수 있다는 것을 알기 때문에, 기초를 확실히 이해하고 넘어가려는 태도가 생겼습니다. 기술 면접에서 "왜 이렇게 동작하는가"를 설명할 수 있는 이유입니다.

지원동기 비전공자로서 채용에서 불리하다고 느끼지 않나요?
▶

처음엔 느꼈습니다. 하지만 DB보안솔루션(829시간) + SeSAC 웹 부트캠프(762시간)로 총 1,591시간의 집중 학습을 했고, 두 팀 프로젝트에서 모두 수상(1차 열정상, 최종 우수상)했습니다. 비전공자이기 때문에 오히려 "왜 이렇게 동작하는가"를 당연하게 여기지 않고 파고드는 습관이 생겼습니다. 이 점이 기술 설명에서 강점이 됩니다.

CafeOn 프로젝트
CafeOn CafeOn 프로젝트를 1분 안에 소개해주세요.
▶

서울 지역 13,000개 이상의 카페 데이터를 Kakao Map API + Selenium으로 수집하고, AI 기반으로 리뷰를 요약해 사용자 취향에 맞는 카페를 추천하는 플랫폼입니다. 프론트엔드 2명, 백엔드 3명으로 5주 진행했으며, 저는 데이터 수집 파이프라인 설계, 카페 검색/추천 API, JWT 인증 전체를 담당했습니다.

CafeOn 13,000개 카페 데이터를 구체적으로 어떻게 수집했나요?
▶

두 단계로 진행했습니다. 1단계: Kakao Map REST API로 서울 각 구별 키워드 검색을 반복해 카페 기본 정보(이름, 주소, 좌표, kakaoId)를 수집했습니다. 2단계: Selenium으로 각 카페 상세 페이지를 크롤링해 영업시간을 수집하고 패턴을 정규화했습니다. Python ETL 스크립트(SQLAlchemy + PyMySQL)로 MySQL에 자동 적재했습니다.

CafeOn Kakao Map API만으로 충분하지 않았나요? Selenium을 함께 쓴 이유는?
▶

Kakao Map API는 영업시간 정보를 제공하지 않거나 부정확한 경우가 많았습니다. 카카오 플레이스 상세 페이지에만 있는 태그나 메뉴 정보가 필요했고, BeautifulSoup 단독으로는 JavaScript 렌더링 후 데이터를 파싱하기 어려워 Selenium으로 실제 브라우저를 구동해 수집했습니다.

CafeOn AI 리뷰 요약과 태그 추출은 어떻게 구현했나요?
▶

Naver Blog에서 카페별 리뷰를 수집한 뒤 HuggingFace Summarizer + OpenRouter API를 활용해 요약문을 생성하고 키워드 태그를 추출했습니다. Python에서 프롬프트 엔지니어링으로 "카페 특징을 키워드로 요약"하는 결과를 얻었고, 추출된 요약문과 태그는 CafeEntity 필드에 저장하며 CafeScheduler로 주기적으로 갱신합니다.

CafeOn 데이터 수집 과정에서 발생한 문제와 해결 방법은?
▶

두 가지가 있었습니다. 첫째, Kakao API rate limit 문제입니다. 구별로 페이지네이션을 나눠 요청 간격을 두고, 결과를 임시 파일에 체크포인트로 저장해 재시작 시 이어받을 수 있게 했습니다. 둘째, kakaoId가 없는 카페의 중복 처리입니다. findByNameIn()으로 이름 기준 매칭하고 existsByKakaoId()로 중복 방지했습니다.

CafeOn 카카오 API 결과와 DB 기존 데이터를 병합하는 로직을 설명해주세요.
▶

CafeService.searchAndMerge()에서 처리합니다. 카카오 API에서 15개 결과를 가져온 뒤, findByNameIn()으로 DB에 이미 있는 카페를 조회합니다. DB에 있는 카페는 kakaoId를 업데이트하고, 없는 카페는 @Async synchronizeCafe()로 비동기 저장합니다. 응답은 DB 결과와 카카오 결과를 병합해 반환합니다.

CafeOn JWT 인증 구조를 설계할 때 가장 신경 쓴 부분은?
▶

Token Rotation 전략입니다. Refresh Token을 DB에 저장하되 갱신할 때마다 새 토큰으로 교체합니다. 탈취된 이전 토큰으로 재시도 시 DB 값과 달라 거부됩니다. Access Token 30분, Refresh Token 14일로 설정해 탈취 피해를 최소화하면서 사용자 편의도 유지했습니다.

CafeOn AWS RDS, EC2, S3를 각각 어떤 용도로 사용했나요?
▶

RDS는 MySQL 데이터베이스 호스팅, EC2는 Spring Boot 애플리케이션 서버, S3는 카페·리뷰·프로필 이미지 저장에 사용했습니다. CDN_BASE_URL 환경변수로 이미지 URL을 구성했고, 서버 재시작 시 데이터 유실을 방지하기 위해 이미지는 반드시 S3에 저장하도록 설계했습니다.

CafeOn 팀 내 백엔드 구조 총괄로서 어떤 결정을 주도했나요?
▶

도메인별 패키지 구조를 설계하고 팀원들에게 컨벤션을 공유했습니다. GlobalExceptionHandler, ApiResponse<T> 공통 래퍼, JWT 필터를 먼저 구현해 팀 전체가 일관된 방식으로 개발할 수 있는 기반을 만들었습니다. 팀원들이 @AuthenticationPrincipal String userId로 바로 주입받을 수 있도록 인증 구조도 제가 설계했습니다.

CafeOn Hot Score 알고리즘을 직접 설계했는데 기준이 무엇이었나요?
▶

views_last7d × w7d + viewCount × wAll + avgRating × 50 × wRate + reviewCount × 5 × wRev 공식을 사용했습니다. 최근 7일 조회수에 가장 높은 가중치를 줘 "지금 뜨는 카페"를 반영했고, 평점과 리뷰 수로 "검증된 카페"도 포함했습니다. 가중치를 쿼리 파라미터로 받아 운영 중 유연하게 튜닝할 수 있도록 설계했습니다.

CafeOn 비동기(@Async) 처리를 도입한 이유는?
▶

카카오 API 검색 응답 시 신규 카페를 DB에 저장하는 작업이 동기로 실행되면 응답 지연이 발생합니다. @Async synchronizeCafe()로 신규 카페 저장을 별도 스레드에서 처리해 검색 API 응답 속도를 보장했습니다. 단, @Async는 public 메서드여야 프록시가 동작하고 호출자의 트랜잭션에 참여하지 않으므로 별도 @Transactional을 선언했습니다.

CafeOn N+1 문제를 실제 프로젝트에서 어떻게 해결했나요?
▶

카페 목록 조회 시 각 카페의 태그와 리뷰를 개별 쿼리로 가져오면 N+1이 발생합니다. findTagNamesByCafeIds(List<Long>)와 getReviewsByCafeIds(List<Long>)로 IN절 배치 쿼리를 작성해 한 번에 가져온 뒤, Map<Long, List<>>로 변환해 각 카페에 매핑했습니다. 조회 쿼리 수를 N+1에서 3개로 줄였습니다.

CafeOn Swagger API 문서화를 통해 협업이 어떻게 개선됐나요?
▶

springdoc-openapi를 설정해 /api-docs에서 확인할 수 있게 했고, Controller에 @Operation, @ApiResponse로 요청/응답 예시를 직접 작성했습니다. 프론트엔드 팀이 별도 문서 요청 없이 Swagger UI에서 직접 테스트할 수 있어 API 변경 시 커뮤니케이션 비용이 줄었습니다.

CafeOn 배포까지 완료하지 못한 이유와 배운 점은?
▶

데이터 수집 파이프라인 구축과 AI 연동에 예상보다 많은 시간이 걸려 배포 단계까지 이르지 못했습니다. BookTalk에서는 배포까지 완료했기 때문에 그 경험이 있었지만, 두 작업을 병행하다 보니 시간이 부족했습니다. 이 경험으로 MVP를 먼저 배포하고 기능을 추가하는 방식의 중요성을 배웠습니다.

CafeOn 지금 다시 설계한다면 바꾸고 싶은 부분은?
▶

세 가지입니다. 첫째, 조회수 UPDATE를 Redis로 버퍼링해 DB 부하를 줄이고 싶습니다. 둘째, 임시 비밀번호 방식을 UUID 토큰 + 만료시간의 일회용 링크로 개선하고 싶습니다. 셋째, 동일 검색어를 반복 호출할 때 매번 카카오 API를 요청하는 구조를 캐싱으로 개선하고 싶습니다.

BookTalk 프로젝트
BookTalk 팀장으로서 가장 힘들었던 순간은?
▶

DB 랜섬웨어 사고가 발생했을 때입니다. Cloud SQL 데이터가 갑자기 사라졌고, 처음엔 원인을 몰라 당황했습니다. 하지만 팀원들에게 "침착하게 원인부터 파악하자"고 하고 직접 GCP 로그를 분석해 랜섬웨어 공격임을 확인했습니다. 새 VM에 Public IP 차단, VPC 내부 전용 접속, 서브넷 구성을 직접 적용해 복구했습니다.

BookTalk 랜섬웨어 사고 후 어떤 보안 조치를 적용했나요?
▶

세 가지를 적용했습니다. 첫째, Public IP를 차단하고 내부 IP 전용 접속으로 변경했습니다. 둘째, VPC 네트워크와 서브넷을 구성해 DB가 외부에서 직접 접근 불가능하게 했습니다. 셋째, UFW(방화벽)로 허용 포트를 최소화했습니다. 이 조치들로 DB 안정성과 보안 리스크를 크게 줄였습니다.

BookTalk Render에서 GCP VM + pm2로 전환한 이유는?
▶

Render 무료 플랜은 비활성 시 슬립 모드로 전환되어 첫 요청에 수십 초 지연이 발생했습니다. GCP VM + pm2 reload로 전환하면서 무중단 서비스가 가능해졌고, 직접 Linux 환경을 구성하며 Nginx 설정, 방화벽(UFW), 프로세스 관리를 실제로 다뤄볼 수 있었습니다.

BookTalk Mixed Content 문제를 어떻게 해결했나요?
▶

Netlify(HTTPS) 프론트에서 GCP VM(HTTP) 백엔드를 호출하면 브라우저가 Mixed Content로 차단합니다. 가비아에서 도메인을 구매하고 Nginx에 리버스 프록시를 설정한 뒤, Certbot + Let's Encrypt로 SSL 인증서를 발급해 HTTPS로 전환했습니다. 이 과정에서 Nginx 설정 파일 구조와 인증서 자동 갱신을 실제로 다뤘습니다.

BookTalk Node.js 경험이 Java/Spring Boot 개발에 어떻게 도움이 됐나요?
▶

Node.js의 미들웨어 체인을 이해하고 나니 Spring의 FilterChain 개념이 훨씬 직관적으로 이해됐습니다. TypeScript로 타입을 명시하는 습관이 Java의 강타입 시스템을 자연스럽게 받아들이는 데 도움이 됐고, Prisma ORM을 먼저 경험했기 때문에 Hibernate JPA의 지연 로딩, 영속성 컨텍스트 개념을 비교하며 이해하기 쉬웠습니다.

BookTalk Prisma ORM과 Hibernate JPA의 차이점은?
▶

Prisma는 schema.prisma 파일로 모델을 정의하고 마이그레이션을 자동 생성합니다. Hibernate JPA는 Java 클래스의 어노테이션으로 Entity를 정의하고 영속성 컨텍스트가 변경감지(Dirty Checking)를 처리합니다. Prisma는 타입 안전한 쿼리 빌더로 자동완성이 좋고, JPA는 지연 로딩과 2차 캐시로 성능 최적화가 유연합니다.

BookTalk Git 브랜치 전략을 어떻게 정했나요?
▶

Git Flow 기반으로 dev 브랜치를 통합 기준으로 삼고, 기능별 feature/ 브랜치를 만들어 PR로 병합했습니다. 팀장으로서 커밋 컨벤션(feat:, fix:, docs:)과 PR 작성 규칙을 먼저 제안해 팀 전체가 일관된 방식으로 협업했습니다. CafeOn에서도 동일한 전략을 적용했습니다.

BookTalk GCP와 AWS를 모두 경험했는데 차이점은?
▶

GCP는 VM 인스턴스 직접 구성(Debian Linux + pm2 + Nginx)으로 인프라 운영의 전 과정을 경험했고, AWS는 RDS/EC2/S3 관리형 서비스를 활용해 인프라 설정보다 애플리케이션 개발에 집중할 수 있었습니다. 스타트업 초기에는 AWS의 관리형 서비스가 운영 부담을 줄이는 데 유리하고, 비용 최적화와 직접 제어가 필요할 때는 GCP VM이 유연합니다.

기술 역량
기술 Spring Boot 프로젝트를 처음부터 시작한다면 어떤 순서로 구성하나요?
▶

1단계: 도메인 분석 후 패키지 구조 설계. 2단계: DB 스키마와 Entity 설계. 3단계: 공통 컴포넌트(ApiResponse, GlobalExceptionHandler, JWT 설정)를 먼저 구현해 팀 전체가 일관된 방식으로 개발할 수 있는 기반 구성. 4단계: 각 도메인의 Repository → Service → Controller 순으로 개발. CafeOn에서 이 순서로 진행했습니다.

기술 Docker를 실제로 사용한 경험이 있나요?
▶

기술 스택에 Docker를 포함했으며, Dockerfile과 docker-compose 작성을 학습했습니다. 실제 프로젝트에서는 EC2에 직접 배포했지만, 컨테이너화를 통해 개발 환경과 운영 환경의 불일치 문제를 해결하는 원리를 이해하고 있습니다. 베스트텍에서 컨테이너 기반 환경이 있다면 빠르게 적응할 수 있습니다.

기술 Nginx를 어떤 역할로 사용했나요?
▶

BookTalk에서 리버스 프록시로 사용했습니다. 클라이언트의 HTTPS(443) 요청을 받아 내부 Node.js 서버(3000포트)로 포워딩하는 역할을 했고, Certbot과 연동해 SSL 인증서 자동 갱신도 처리했습니다. 로드 밸런서, 정적 파일 서빙, 요청 로깅에도 활용할 수 있다는 것을 학습했습니다.

기술 Redis를 기술 스택에 포함한 이유와 실제 사용 경험은?
▶

CafeOn에서 조회수 UPDATE 최적화 개선 방향으로 Redis 버퍼링을 검토했고 개념적으로 학습했습니다. 솔직히 실제 적용까지는 하지 못했습니다. 포트폴리오에 포함한 것은 "이 문제를 Redis로 해결할 수 있다는 판단 능력이 있다"는 의미로 기재했으며, 베스트텍에서 실무를 통해 실제 적용 경험을 쌓고 싶습니다.

기술 DB 스키마 설계에서 가장 신경 쓰는 부분은?
▶

세 가지입니다. 첫째, 정규화와 성능의 균형입니다. 조회가 많은 데이터는 JOIN보다 비정규화가 나을 수 있습니다. 둘째, 자주 조회되는 컬럼(userId, cafeId)에 인덱스 설정입니다. 셋째, Enum 타입은 EnumType.STRING으로 저장해 Enum 순서 변경에 따른 데이터 오염을 방지합니다.

기술 새로운 API나 라이브러리를 처음 연동할 때 어떻게 접근하나요?
▶

세 단계로 접근합니다. 1단계: 공식 문서를 먼저 읽고 rate limit, 인증 방식, 응답 형식을 파악합니다. 2단계: Postman으로 직접 API를 호출해보며 실제 응답을 확인합니다. 3단계: 코드에 통합하면서 예외 상황(timeout, 빈 응답 등)을 처리합니다. Kakao Map API와 OpenRouter API 연동 시 이 방식으로 접근했습니다.

기술 Spring Boot와 Node.js 중 어느 것이 더 적합한 상황은?
▶

Spring Boot는 엔터프라이즈급 복잡한 비즈니스 로직, 강타입 보장, 트랜잭션 관리가 중요할 때 적합합니다. Node.js는 I/O 바운드 작업이 많고 빠른 프로토타이핑이 필요할 때 유리합니다. 바이브코딩 솔루션처럼 안정적인 백엔드 아키텍처와 보안이 중요한 서비스에는 Spring Boot가 더 적합하다고 생각합니다.

기술 무중단 배포란 무엇이며 어떻게 구현했나요?
▶

서비스 중단 없이 새 버전을 배포하는 방식입니다. BookTalk에서 pm2 reload로 구현했습니다. pm2 reload는 기존 프로세스를 유지하면서 새 버전으로 순차 교체합니다. Spring Boot에서는 Blue-Green 배포나 Docker + Nginx로 구현하며, 포트 스위칭 방식으로 다운타임 없이 전환합니다.

기술 REST API 설계 원칙을 어떻게 적용했나요?
▶

리소스를 명사로 표현하고(/api/cafes, /api/reviews) HTTP 메서드로 행위를 구분했습니다. 다만 /api/auth/logout처럼 동작이 복잡한 경우 순수 REST보다 실용적인 URL을 선택했습니다. ApiResponse<T> 래퍼로 모든 응답을 {"message": "...", "data": {...}} 형태로 통일해 프론트엔드가 응답 형식을 예측할 수 있게 했습니다.

기술 OpenRouter API를 통한 AI 연동 경험을 설명해주세요.
▶

Naver Blog에서 수집한 카페 리뷰 텍스트를 OpenRouter API에 전달해 요약문과 태그 키워드를 추출했습니다. Python에서 프롬프트 엔지니어링으로 "카페 특징을 3개 키워드로 요약"하는 결과를 얻었고, 응답 JSON을 파싱해 DB에 저장했습니다. 모델 응답 지연이 있어 배치 처리로 야간에 실행하도록 설계했습니다.

인성 & 커리어
인성 "끝까지 파고드는 태도"의 구체적 사례를 들어주세요.
▶

BookTalk에서 Cloud SQL DB가 갑자기 사라졌을 때입니다. "DB가 없어졌다"는 사실에 당황하지 않고 GCP 로그를 직접 분석해 랜섬웨어 공격임을 확인했습니다. 단순히 새 DB를 만드는 것이 아니라 공격 원인인 Public IP 노출 문제를 근본적으로 해결하기 위해 VPC 내부 전용 접속, 서브넷 구성까지 직접 적용했습니다.

인성 약점인 "새 기술에 깊이 파고드는 경향"을 어떻게 조절하고 있나요?
▶

"일단 동작하는 버전을 먼저, 이해는 안정화 단계에서"라는 원칙을 세웠습니다. AWS 인프라 구성 시 처음엔 설정 원리를 전부 이해하려다 일정이 지연됐습니다. 이후로는 먼저 동작하는 최소 구현을 만들고, 코드 리뷰나 리팩토링 단계에서 깊이 이해하는 방식으로 조정하고 있습니다.

인성 팀에서 의견 충돌이 있었을 때 어떻게 해결했나요?
▶

배포 방식을 두고 팀원과 의견이 달랐습니다. 한 팀원은 간편한 Render를 선호했고 저는 GCP VM을 제안했습니다. 장단점을 정리한 비교표를 만들어 팀에 공유하고, "성능과 비용 외에도 직접 운영 환경을 경험해보는 것이 학습 목적에 맞다"는 근거를 들어 설득했습니다. 감정이 아닌 데이터와 근거로 설득하는 방식을 선호합니다.

인성 팀 프로젝트에서 본인의 기여도가 얼마나 됐다고 생각하나요?
▶

CafeOn에서는 백엔드 3명 중 데이터 수집 파이프라인 전체, JWT 인증, 카페 검색 API, Wishlist, Review API를 담당했으니 백엔드 기여도의 60% 이상은 맡았다고 생각합니다. 또한 공통 구조(패키지 설계, ApiResponse, GlobalExceptionHandler, JWT 필터)를 제가 설계해 팀원들이 기반 위에서 개발할 수 있었습니다.

인성 짧은 기간에 두 개 기술 스택(Java, Node.js)을 배운 비결은?
▶

핵심 개념은 언어가 달라도 같다는 것을 이해했습니다. HTTP 요청/응답, ORM, JWT 인증, 배포 구조는 어느 스택에서나 동일합니다. Node.js로 구조를 먼저 이해하고 Java로 같은 개념을 재구현하면서 "이 언어가 이 개념을 어떻게 구현하는가"에 집중했습니다.

인성 이 회사에서 가장 빠르게 기여할 수 있는 부분은?
▶

Spring Boot 기반 REST API 설계와 JWT 인증 구조입니다. CafeOn에서 이 두 가지를 처음부터 구현한 경험이 있어 바이브코딩 솔루션 초기 백엔드 아키텍처 구축에 즉시 기여할 수 있습니다. Swagger API 문서화, 공통 예외 처리 구조, 도메인별 패키지 설계도 빠르게 세팅할 수 있습니다.

인성 실수를 했을 때 어떻게 대처하나요?
▶

먼저 원인을 파악합니다. 랜섬웨어 사고처럼 큰 실수도 "왜 일어났는가"를 분석해야 재발을 막을 수 있습니다. 다음으로 팀에 즉시 공유합니다. 숨기면 더 큰 문제가 됩니다. 마지막으로 문서화합니다. BookTalk 트러블슈팅을 포트폴리오에 상세히 기록한 이유도 같은 실수를 반복하지 않기 위해서입니다.

인성 인턴십 이후 정규직 전환 시 어떤 방향으로 성장하고 싶나요?
▶

단기적으로는 초기 아키텍처 구축 경험을 바탕으로 서비스가 성장하면서 발생하는 성능 이슈와 스케일링 문제를 함께 해결하고 싶습니다. 중장기적으로는 AI 기능과 백엔드 인프라를 연결하는 파이프라인 설계로 발전하고 싶습니다. CafeOn에서 AI API를 백엔드에 연동한 경험이 그 방향의 시작점이 됐습니다.

인성 3년 후 어떤 개발자가 되고 싶나요?
▶

"AI 서비스를 실제로 떠받치는 백엔드 개발자"입니다. AI 모델 결과를 사용자에게 안정적으로 전달하는 API 설계, 대용량 데이터 처리 파이프라인, 인프라 운영까지 책임질 수 있는 개발자가 되고 싶습니다. 베스트텍의 AIXR 솔루션 환경이 그 방향을 가장 깊이 키울 수 있는 무대라고 생각합니다.

인성 마지막으로 하고 싶은 말이 있나요?
▶

바이브코딩 솔루션의 초기 백엔드 아키텍처를 직접 설계하는 경험은 개발자 커리어에서 매우 드문 기회입니다. 저는 CafeOn에서 13,000개 데이터 파이프라인과 REST API를 처음부터 혼자 설계해본 경험이 있습니다. 음악에서 배운 것은 "혼자 잘하는 것보다 함께 만들어가는 결과물이 더 크다"는 것이었습니다. 그 마음으로 팀에 기여하는 개발자가 되겠습니다. 잘 부탁드립니다.
